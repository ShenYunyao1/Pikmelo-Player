# Pikmelo Player 客户端与在线服务器初步方案

更新日期：2026-11-11

## 目标

构建 Flutter 跨平台音乐播放器，首期至少支持 Windows 与 Android。播放器通过 API Key 连接现有 Pikmelo Server，同步获授权的曲库、歌单及曲目元数据，并将用户选择的音频下载至本机，使下载完成的曲目在断网时仍可播放。

“同步歌单”与“同步音频文件”是两个独立过程。服务端 `/sync` 同步目录和歌单等元数据，离线播放要求音频已成功下载到本地。

## 总体结构

```text
Flutter 客户端（Windows / Android）
  ├─ 播放器与播放队列
  ├─ API Key 凭据存储
  ├─ 本地 SQLite 元数据、歌单与同步游标
  ├─ 音频缓存目录与下载任务
  └─ 同步协调器、网络状态与冲突恢复
                 │ HTTPS + REST API v2
                 ▼
Pikmelo Server（Go 服务）
  ├─ API Key 认证与资源授权
  ├─ SQLite 元数据数据库（WAL）
  └─ 本地媒体目录（音频、封面、歌词）
```

客户端将服务端地址、账户/服务器标识、曲目 UUID、元数据、歌单成员顺序及离线文件状态保存在本机。音频文件与元数据分开管理，缓存记录包含服务端来源和文件状态，避免把尚未下载完成的音频显示为可离线播放。

## 客户端连接与权限

1. 用户在 Pikmelo Server 网页端创建播放器 API Key，并明确授权 `library:read`、`media:read` 及需要同步的私人歌单或全局 `library`。
2. 客户端设置页输入服务器 HTTPS 地址和 API Key，调用健康检查及只读接口验证连接。
3. 请求头按服务端协议使用 `X-API-Key` 或 `Authorization: Bearer <key>`。Key 创建/轮换后仅显示一次，客户端应使用 Windows 与 Android 各自的受保护凭据存储，避免明文写入配置、日志或数据库。
4. Key 默认没有歌单授权。无权访问、Key 失效或授权被撤销时，显示明确状态并执行服务器要求的缓存权限重置。

服务端 Key 是只读播放器凭证。歌单和曲目上传、编辑仍由服务器网页端或其他具备相应会话权限的管理入口完成。

## 元数据同步

- 首次连接请求 `GET /api/v2/sync?limit=100` 获取完整快照。后续请求携带上一页返回的 `cursor`，按序处理所有 `has_more=true` 页面。
- 每页最多 500 项。响应中的 `changed_tracks`、`playlists`、`deleted_tracks`、`deleted_playlists`、`cursor`、`full_snapshot`、`reset` 和 `revision` 按 UUID 更新本地投影。
- 在本地数据库事务中应用整轮分页结果，所有页面成功后才提交最终 cursor，避免中断时留下不一致进度。不能用 `revision` 替代 cursor。
- 收到 `reset=true` 时按协议清理该服务器旧快照，再应用新快照。`deleted_tracks` 表示删除可用曲目缓存，不应因此删除歌单中的成员 UUID、顺序或个人备注。不可用成员以占位记录呈现。
- `409 SYNC_RESTART` 时丢弃本轮未提交的快照分页并从不带 cursor 的请求重试。游标过期或权限范围变化也可能触发重置。游标有效期为 24 小时，客户端应在应用启动、回到前台和联网恢复后及时完成增量同步。
- 第一版采用启动/前台恢复时同步，加播放过程中低频轮询的策略，不依赖长连接。同步请求按服务端 Key 元数据并发限制排队，处理 `429` 时遵守 `Retry-After`。

## 离线音乐与播放

- 歌单详情展示曲目元数据，并区分“可在线播放”“下载中”“已下载可离线播放”“下载失败”状态。
- 用户可对单曲或歌单执行“下载到本地”。后台下载器使用 `GET /api/v2/media/{id}`，支持服务端的 HTTP Range 与 ETag，提供进度、暂停/继续、失败重试和取消。
- 下载先写入临时文件，验证完整响应长度后再原子改名并标记完成。失败或取消清理临时文件，保留已有有效缓存。必要时可通过 Range 恢复中断任务，须遵循服务端对 ETag/Range 的实际响应行为。
- 播放源按本地有效缓存优先，否则在线流式读取。断网时播放已完整下载的音频，未下载曲目保留歌单位置并提示需联网下载。
- Android 将音频存储到应用专属持久目录，Windows 使用应用数据目录下的专属缓存目录。加入缓存容量统计、单曲/歌单删除和“清理未被歌单引用的缓存”入口。
- 已下载音频是离线副本。Key 或权限撤销后，客户端重新联网同步时清理服务器明确撤销的元数据/授权状态；网络断开期间设备只能依据最后成功取得的本地状态工作，服务端无法即时撤回设备上的文件。

## 在线服务器部署

首选沿用 `ShenYunyao1/Pikmelo-Server`，不在播放器项目中重写账号、Key、媒体库或同步 API。

- 服务端仓库提供 Go 服务、SQLite 数据库和本地媒体存储。线上建议部署在 Ubuntu 22.04/24.04、Linux amd64、systemd 主机，发行包可预编译并验签后安装，云主机不需要 Go 编译环境。服务运行需要 `ffprobe`（由 FFmpeg 提供）。
- 规划固定数据盘和备份容量。SQLite WAL 数据目录必须使用支持文件锁的本地可写文件系统，不放在 NFS/SMB 等网络共享目录。音频媒体目录与数据库运行目录按仓库部署要求分离并持久化。
- 使用域名和 HTTPS 反向代理。公网入口仅开放 SSH 与 HTTPS（按证书签发方式可能还需 HTTP 80），服务后端保持 `127.0.0.1:8080`，防火墙及云安全组禁止公网直连 8080。
- 设置 `MUSIC_SERVER_PUBLIC_URL` 为实际 HTTPS 地址。部署后创建管理员，再由管理员创建成员账号和播放器 Key，按最小权限授权歌单。
- 配置定期完整备份并实际演练恢复。数据库备份和音频文件都需要保护，TLS 私钥、反向代理和系统服务配置应单独备份。
- 先在个人测试机或隔离环境验证 Windows、Android 对真实 HTTPS 服务的认证、分页、下载、Range、恢复及离线播放，再作为正式线上服务器使用。

## 建议实施阶段

1. **协议接入验证**：固定 API 基础地址配置方式，实现 Key 输入、健康检查、`/sync` 快照/增量和错误状态显示。
2. **本地数据层**：设计本地曲目、歌单、成员、下载任务和游标表，完成幂等分页应用及 reset/restart/权限变化恢复。
3. **在线播放与离线下载**：接入媒体 Range 请求、可靠下载任务、缓存管理，并验证 Windows 与 Android 音频播放。
4. **跨平台体验**：实现播放队列、后台/前台同步、Android 生命周期处理、Windows 桌面交互和网络断开提示。
5. **部署与验收**：部署隔离服务器，检查 TLS、备份恢复、Key 权限和缓存边界，分别生成 Windows 与 Android 构建产物。

## 第一阶段验收条件

- 用户可配置服务器地址和 API Key，未授权歌单不会混入列表。
- 首次全量与后续增量同步可重复运行，分页中断、`SYNC_RESTART`、过期 cursor 和 reset 均不会造成部分状态被误认为完整。
- 同一账号的 Windows 与 Android 客户端在联网后能看到服务器端一致的歌单及曲目元数据。
- 用户下载完成的音频在断网、重启应用后仍能播放；未下载曲目明确显示离线不可用。
- 下载中断不会留下可播放的半文件，恢复联网后能够安全续传或重新下载。
- 服务端 Key 被撤销或歌单授权改变后，联网客户端会按新快照清理失去授权的可见数据。

## 待核实项

当前参考仓库 `server/README.md` 标注版本 0.21.18、SQLite schema 9，但 `server/deploy/README.md` 的开头仍标注 schema 8。线上部署前需要以目标正式 Release 的清单、迁移说明和实际程序为准，先核对部署文档与发行资产版本，避免按过时 schema 指引升级。

需在客户端实现前进一步核实 `/sync` 与 `/media/{id}` 的完整 JSON 字段、ETag/Range 边界行为，以及在线服务器实际网络地址和容量。此方案按当前仓库文档作为初步设计，没有假设已经存在可用公网主机。
